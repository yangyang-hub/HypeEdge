## 阶段 0 — 系统止血（让系统真实可下单）

### P0-1 【C1】SafetyController 永久停在 Starting → 全系统拒单（静默停摆）
- **位置**：`crates/app/src/runtime.rs:302-304`（构造 Starting）、`:525-531`（对外状态硬编码）、`crates/trading/src/risk/safety.rs:71-88`（Starting 拒绝）、engine.rs:226-232/:566-572/:1492
- **修复**：
  1. 启动对账/账户就绪后显式 `safety.transition(SafetyMode::Normal)`（放 poller 首次成功 + 历史恢复完成之后）；
  2. `trading_enabled`/`safety_mode` 不再无条件写死，改为由 `!kill_switch.is_active()` 与 SafetyController 真实状态派生（或经 EventBus 同步），消除虚假健康；
  3. `risk_status` 的 `safety_reason` 字段语义修正（现在把 mode 当 reason）。
- **测试**：新增装配级端到端测试：完整 runtime wiring（内存/测试 PG）下 `submit_order` 必须通过 run_gates 到达 engine；SafetyController Starting→Normal 转移测试；kill switch 触发后 `trading_enabled=false` 断言。

### P0-2 【C2】`account_state.action_credits_remaining` 生产恒 NULL → DB 风控解码报错 → 主路径全断
- **位置**：`crates/storage/src/account_state_store.rs:41-56`（UPSERT 缺列）、`rows.rs:169`（非 Option i64）、`durable_order_store.rs:250-265`（SELECT * 解码点）
- **修复**：
  1. `rows.rs` 改为 `action_credits_remaining: Option<i64>`（该字段暂无风控消费方，零风险）；
  2. UPSERT 中补该列（取 `userRateLimit` 快照值），保持数据可用；
  3. 顺带检查同类行结构问题：`OrderRow.command_id`（H-PG1，见 P2-5）、`RiskReservationRow.command_item_id`（M-PG1）。
- **测试**：新增集成测试——用生产写入路径（`PostgresAccountSnapshotStore::persist` 模拟 poller）写 NULL 后 `persist_placement(dispatch=true)` 必须成功；再测写非 NULL 后成功。

### P0-3 【回归防线】补装配级端到端测试框架
- 上轮 C1/C2 漏网根因：单测全部用 `safety: None`、测试 seed 非 NULL。建立最小装配测试（InMemory store 或测试 PG）：`AppRuntime` 简化装配 → 真实 `submit_order` 全链路 → 断言订单到达 MockExchange。此测试作为后续每个阶段的回归网。

## 阶段 1 — 交易链路安全（资金相关 HIGH）

### P1-1 【C3】签名 HTTP 路径零超时 → 单次挂起永久卡死全部交易
- **位置**：`crates/trading/src/execution/exchange.rs:79`（`reqwest::Client::new()`）、`nonce.rs:86-92`（worker 无 per-action 超时）、`engine.rs:551-637/:1690-1723`（update_leverage 无调用方超时）
- **修复**：client `timeout(10s)+connect_timeout(5s)`（对齐 rest_client）；NonceQueue worker 内每个 action 套 `tokio::time::timeout`，超时记录并继续（nonce 已分配不回收）；`update_leverage` 加与 submit 一致的 3s 包装；cloid 查询（engine.rs:655/662）同样加超时。
- **测试**：MockExchange 挂起场景：worker 在超时后继续处理后续动作；update_leverage 超时返回错误不卡队列。

### P1-2 【C5】趋势策略把未收盘 K 线盘中更新当独立 bar 追加
- **位置**：`crates/trading/src/strategy/trend_follow.rs:364-374`（无去重）、`ws_feed.rs:220-245`（原样转发）
- **修复**：策略侧按 `(symbol, interval, timestamp)` 去重——仅当 timestamp 推进（bar 完成）才 append 且 `candle_count += 1`；校验 `candle.interval == 配置 interval`（多 interval 订阅时不混入）。
- **测试**：构造同 timestamp 多条 CandleUpdate → 断言 closes 只 append 一次、candle_count 只 +1；interval 不匹配的帧被忽略。

### P1-3 【H-PG3】DB 级 max_position 门符号错误（fail-open）

### P1-4 【H-EX5】ingestor 不发布 OrderFilled → 趋势策略挂单成交后永久卡死

### P1-5 【H-ST2..4】趋势策略四项 HIGH

### P1-6 【H-RK1/RK2】A16 修复三处回归（参考价信任订单自身价）

## 执行纪律

1. **每项修复遵循**：先写回归测试（红）→ 实现（绿）→ `cargo test -p <crate>` + `cargo clippy -D warnings` 全绿 → 提交。
2. **小步提交**：每项一个 commit，方便回滚。
3. **阶段门禁**：每阶段完成后跑 `make lint && make test` 全量 + 前端 `pnpm typecheck && pnpm test`。
4. **涉及枚举/事件/DB schema 的改动**：同步 `as_str()`/ALL_EVENT_TYPES/迁移文件/design.md 相关章节（AGENTS.md 红线）。
5. **顺序依赖**：P0 → P1 → P2 严格串行；P3/P4/P5 可与 P2 并行（不同 crate，前端与后端可并行）。
6. **验收口径**：修复后重新跑对应子代理审计范围的自检清单（每项附回归测试即视为闭环）。
